# Autonomous project workflows

Project work is stored in the workspace SQLite database. A kickoff conversation remains the source of collaborative context. The user creates goals, explicitly asks a coordinator for a proposal, edits it if needed, and approves it before task execution starts. Session Agent roles are project-local strings; the UI suggests an active Session Agent whose role is `Director` as coordinator, then falls back to the first active authorized collaborator. The persisted coordinator remains explicit on the proposal.

Tasks, task dependencies, attempts, current request keys, execution IDs, deliverable references, consultation status, and workflow events persist in SQLite. The worker checks the existing Collaboration execution records before creating an activation, and uses stable idempotency keys for each planning request and task attempt. On restart it inspects the persisted execution; uncertain or interrupted executions are surfaced for explicit owner review and retry. Page content is stored in the project Space, with task, execution, author, version, and review status recorded as deliverable provenance.

The current workflow does not continue a guided meeting autonomously after the user replies. The extension point is `ProjectWorkService.processTaskExecution` / the task continuation path in `src/server/project-work.ts`, after a human-authored message is added to the kickoff conversation and before the next explicit task activation. A future facilitator can be identified through the persisted `coordinatorSessionAgentId` (selected from an active Session Agent with role `Director` where available), then submit a separately authorized activation using the existing CollaborationService and ACL checks. That continuation must be bounded, persisted, idempotent, and paused until a user explicitly opts in; this document does not enable it.
